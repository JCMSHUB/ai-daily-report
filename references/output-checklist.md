# AI 情报简报发布前最终自检清单

Version: 3.2

---

# Purpose

本文件定义发布前最终检查流程。目标不是让简报更完整，而是让简报对个人注意力分配、工具选择、学习重点和后续行动更有用。

---

# Stage 1 — Event Selection Review

发布前必须先完成候选事件筛选表。筛选表可以不写入最终简报，但必须覆盖：

- 事件。
- 主要来源。
- 综合评分。
- 证据类型。
- Verification 状态。
- 入选栏目或剔除原因。

检查候选事件是否满足：

- 来源可信。
- 信息可验证。
- 存在事实增量。
- 至少具备技术价值、战略价值、试用价值、行动价值之一。
- 已按底层事件完成去重；转载数量不被误当成独立信号。
- 只有入围候选进入 Verification，且已优先复用 Discovery 获得的原始 URL。
- 每个入选事件都有可解释的评分与入选栏目；每个剔除事件都有具体剔除原因。

剔除：

- 无技术内容的融资新闻。
- PR 宣传稿。
- SEO 内容。
- 洗稿转载。
- 名人评论。
- 社交媒体争议。
- 只能制造热闹但不能影响判断或行动的信息。

---

# Stage 2 — 今日结论 Review

对应模板章节：`今日结论`

要求：

- 3-5 条。
- 每条是直接判断，不是新闻标题。
- 每条能说明对技术判断、工具选择、学习重点或产业观察的影响。
- 不得写成“XX 发布了 YY”这种新闻列表。

不合格：

- “OpenAI 发布新模型。”
- “AI 行业持续发展。”
- “值得持续关注。”

合格：

- “Agent 工具链的竞争焦点正在从模型能力转向运行时权限、长期任务和企业系统接入，后续应优先跟踪 MCP、Computer Use 与企业 Agent Runtime。”

---

# Stage 3 — 值得跟踪 Review

对应模板章节：`值得跟踪`

每条必须包含：

- 发生了什么。
- 为什么值得跟踪。
- 观察窗口。
- 下次检查什么。
- 具体信源链接。

要求：

- 通常 2-4 条。
- 不能和“值得尝试”“可以忽略”重复。
- 必须有明确后续检查对象，例如 release、benchmark、API 文档、监管文件、价格页、财报或官方公告。

---

# Stage 4 — 值得尝试 Review

对应模板章节：`值得尝试`

只允许进入：

- 工具。
- 模型。
- 框架。
- repo。
- API。
- 论文。
- 产品。

每条必须包含：

- 适合场景。
- 试用理由。
- 试用成本。
- 入口链接。

如果当天没有值得亲自试用或阅读的对象，可以省略本节。不得为了完整性硬凑。

---

# Stage 5 — 可以忽略 Review

对应模板章节：`可以忽略`

要求：

- 通常 2-4 条；若没有明显占据信息流且值得专门解释的噪音，可以省略本节。
- 必须说明忽略原因。
- 忽略原因必须具体，例如：
  - 缺少一手信源。
  - 只有 PR 叙事。
  - 无技术增量。
  - 短期不可行动。
  - 与工具选择、学习重点或产业判断无关。

禁止只写“价值不高”“无需关注”。

禁止为了保留本节追加低价值搜索或硬凑内容。

---

# Stage 6 — 趋势判断 Review

对应模板章节：`趋势判断`

要求：

- 300-600 字。
- 只讲一个趋势命题。
- 必须包含支持信号、反证条件、观察指标。
- 不得复述前文事件。
- 不得为了输出趋势而输出趋势。

趋势判断至少需要 2 个独立事件或 1 个强一手信源 + 1 个交叉验证信号支持。

若信号不足，可以省略本节；若保留标题，必须写“今日无足够独立信号形成趋势判断”。

---

# Stage 7 — 我的行动清单 Review

对应模板章节：`我的行动清单`

要求：

- 最多 3 条。
- 每条必须是可执行动作。
- 动作类型限定为：阅读、试用、跟踪。
- 必须说明目的。

不合格：

- “关注 AI 行业发展。”
- “继续观察 Agent。”

合格：

- “试用：open-computer-use，目标：验证其是否能替代闭源 Computer Use API 完成浏览器自动化任务。”

---

# Stage 8 — Fact Quality Review

所有核心事实必须包含：

1. Entity
2. Action
3. Object
4. Result

高风险事实，如融资、估值、IPO、监管命令、benchmark、芯片参数、模型能力，必须有官方文件、监管文件、论文/模型卡、GitHub、API 文档或高质量具体报道页支持。

技术事件若已有完整原始材料，可直接通过；商业事件必须具备两个独立高质量来源；治理事件必须优先核对监管机构或官方文件。

禁止使用媒体首页、作者页、主题页、搜索页作为事实信源。

每条核心内容必须能说明证据类型：官方公告、GitHub、Hugging Face、arXiv、API 文档、监管文件、论文、模型卡或两个独立高质量报道。

---

# Stage 9 — Formatting Review

禁止：

- HTML 标签。
- style 属性。
- iframe。
- 内嵌 CSS。
- 富文本格式。
- Markdown 引用块 `>`。

要求：

- 使用标准 Markdown。
- 标题层级连续。
- 信源使用普通列表。
- 正文不使用复杂嵌套。
- 单条 bullet 不超过 180 字。
- 不得为了满足字数扩写、重复表达、加入空泛分析，或把数字改写成中文大写/口语表达来凑字数。

---

# Stage 10 — Publishing Review

发布链路检查：

- Markdown 文件生成成功。
- `python3 scripts/save-to-getnote.py` 执行成功。
- 返回有效访问链接。
- 已归档至知识库。

若任意一项失败，简报不得视为发布成功。

本地 Markdown 保存只作为故障保底产物，不等同于发布成功。

---

# Final Reader Test

发布前最终检查：

如果读者只阅读：

- 今日结论
- 我的行动清单

是否能够知道：

```text
今天哪些信息值得投入注意力，以及下一步该做什么？
```

如果不能，重新组织内容。
